# 智能医疗项目：高并发挂号流程完整设计说明

## 1. 先说结论

我们这个高并发挂号流程，核心目标不是“让数据库完全不参与”，而是：

1. 先用 Redis 在入口挡住大部分失败请求
2. 只让真正抢到号的人进入后续数据库链路
3. 用本地消息表保证“成功请求不会丢”
4. 用异步消费把最终挂号单和数据库库存落下来

所以整套方案本质上是：

`Redis 预扣库存 + 本地消息表 + Kafka 异步消费 + 数据库最终落账`

它解决的重点是两个问题：

1. 高并发下不能超卖
2. Redis 扣了库存以后，后面失败不能把库存丢掉

---

## 2. 为什么不能直接用数据库硬扛

假设一个排班只有 20 个号，但是同时有 300 个患者抢号。

如果没有 Redis 这一层，通常会发生这些事情：

1. 300 个请求都同时打到数据库
2. 都去查库存、改库存、插挂号单
3. 数据库锁竞争非常激烈
4. 性能抖动明显，甚至可能超卖

而我们现在的思路是：

1. 300 个请求先到 Redis
2. Redis 只放 20 个继续走
3. 剩下 280 个直接失败
4. 数据库只处理那 20 个真正抢到号的人

所以它不是“数据库没压力”，而是把压力从：

- 所有请求都打数据库

变成：

- 只有成功请求才打数据库

这在高并发场景下差别非常大。

---

## 3. 整体链路总览

当前挂号高并发链路可以拆成 7 步：

1. 前端发起极速挂号请求
2. 服务端做限流
3. 服务端做患者维度防重锁
4. Redis 预扣库存
5. 写本地消息表
6. 定时扫描本地消息表并发送 Kafka
7. Kafka 消费者真正扣数据库库存并生成挂号单

你可以把它理解成两层库存：

1. Redis 库存：入口闸门库存
2. 数据库库存：最终账本库存

Redis 负责“先占坑”，数据库负责“最终记账”。

---

## 4. 第一步：前端发起极速挂号

入口方法是：

- `RegistrationServiceImpl.quickRegister()`

它对应的是“极速挂号”场景，不是传统那种同步写挂号单的慢路径。

调用这个方法后，当前请求线程的目标不是立刻生成最终挂号单，而是：

1. 先判断能不能抢到名额
2. 如果抢到，就把这件事可靠记录下来
3. 后续交给异步流程慢慢落库

所以 `quickRegister()` 的成功语义是：

- “挂号请求已经受理”

不是：

- “挂号单已经同步创建完成”

---

## 5. 第二步：先做限流

代码里先执行了 Lua 限流脚本：

- key：`rate_limit:registration:{scheduleId}`

它的作用不是控制库存，而是防止短时间内请求量瞬间压爆服务。

也就是说，这一层解决的是：

- 同一秒内冲进来的人太多，服务能不能扛住

它解决不了超卖，但能解决“入口洪峰”。

所以你可以把限流理解成：

- 第一层防线：挡洪水

---

## 6. 第三步：患者维度防重锁

接着会用 Redisson 分布式锁：

- key：`req:lock:{patientId}:{scheduleId}`

它的目标是防止同一个患者在极短时间内疯狂重复点击。

这里要注意，它锁的不是整个排班，而是：

- 某个患者对某个排班的一次抢号行为

所以它不是全局串行，不会把所有请求都锁死。

它解决的是：

1. 同一个患者多次重复点击
2. 同一患者重复提交导致重复扣库存

你可以把它理解成：

- 第二层防线：挡重复提交

---

## 7. 第四步：Redis 预扣库存

这是整套并发设计的核心。

代码会对下面这个 key 做 `decrement`：

- `schedule:stock:{scheduleId}`

### 7.1 它为什么快

因为 Redis 的自减是内存级原子操作，性能非常高。

所以当 300 个线程同时过来时：

1. Redis 会非常快地完成库存递减
2. 前 20 个能拿到非负结果
3. 后面的线程会扣成负数

### 7.2 为什么扣成负数还要再加回去

如果扣完发现 `< 0`，说明已经没号了。

这时要马上 `increment` 回去，目的是：

1. 把多扣掉的这一次恢复掉
2. 保持 Redis 中的库存值整洁

所以这一步之后只有两种结果：

1. 成功：这个请求抢到了一个 Redis 名额
2. 失败：库存恢复，直接返回“号源已满”

### 7.3 这一步解决了什么

它解决的是：

- 高并发入口的超卖问题

因为只有抢到 Redis 名额的人才有资格继续往下走。

---

## 8. 第五步：写本地消息表

Redis 扣成功以后，当前代码不会直接写 `registration` 挂号单表。

而是先写一条本地消息记录：

- 表：`registration_message_log`

这张表里保存的是：

1. `msgId`
2. `scheduleId`
3. `patientId`
4. `payload`
5. `status`
6. `retryCount`
7. 时间戳

### 8.1 什么叫“本地消息表”

这里的“本地”不是内存，而是：

- 跟当前业务服务在同一个数据库里的消息表

它本质上就是一张普通数据库表，只是里面存的是“待异步处理的事件”。

### 8.2 为什么不直接发 Kafka

因为如果流程变成：

1. Redis 扣库存
2. 直接发 Kafka

那么一旦在“Redis 扣成功”和“Kafka 发送成功”之间服务崩了，就会出问题：

1. Redis 已经少了一个号
2. Kafka 没发出去
3. 数据库里也没有记录
4. 这格号就丢了

而本地消息表的意义就是：

- 先把“这个成功请求确实存在”落进数据库

只要本地消息表写成功，这件事就不会凭空丢失。

---

## 9. 第六步：这次修掉的 Redis 库存一致性问题

这是这次修复的重点。

### 9.1 旧问题是什么

旧逻辑是：

1. Redis 先扣库存
2. 再 `insert registration_message_log`

如果第 2 步失败，就会出现：

1. Redis 库存已经少了 1
2. 本地消息表没写进去
3. 后续异步流程根本不知道有这次抢号
4. 这个库存就丢了

### 9.2 为什么单纯 try/catch 不够

因为 `@Transactional` 的事务真正提交，发生在方法返回之后。

也就是说，有两种失败：

1. 方法执行中间直接抛异常
2. 方法执行完了，但事务提交阶段失败

如果只在方法体里 `try/catch`，只能接住第 1 种，接不住第 2 种。

### 9.3 现在怎么修的

现在的修法是：

1. Redis 扣减成功后，立刻注册事务完成回调
2. 如果当前事务最终 `ROLLBACK`
3. 就自动把 Redis 库存 `increment` 回去

这样不管是：

1. `messageLogMapper.insert(log)` 直接抛异常
2. 事务提交阶段失败

都会触发补偿。

### 9.4 这次修复的本质

不是把架构推翻重写，而是把现有架构补完整：

- 仍然保留 Redis 预扣
- 仍然保留本地消息表
- 只是把“事务回滚时 Redis 要补回”这件事补上了

这是最小改动且最稳的方案。

---

## 10. 第七步：定时扫描本地消息表

本地消息表写成功后，当前请求其实就可以返回了。

后面由：

- `RegistrationMessageProducer.scanAndSendMessages()`

定时去扫描：

- `status = 0`

的消息。

它的职责是：

1. 找到待发送消息
2. 把消息发到 Kafka
3. 发成功后把状态更新为已发送
4. 发失败则增加重试次数

这一步的意义是：

- 当前请求线程不用同步等待 Kafka

也就是说，请求链路更短，响应更快。

---

## 11. 第八步：Kafka 消费者真正落数据库

真正的数据库扣库存和挂号单生成，不是在 `quickRegister()` 里做，而是在：

- `processRegistrationMessage(...)`

里做。

消费者收到消息后，当前逻辑会：

1. 查询 `doctor_schedule`
2. 扣减数据库 `available_count`
3. 插入 `registration` 挂号单

所以最终业务结果的落账发生在这里。

这一步你要特别记住：

- Redis 预扣不是最终结果
- 数据库扣减才是最终账本

---

## 12. 为什么说它是“两层库存”

### 12.1 Redis 库存

角色：

- 入口并发控制
- 快速挡住失败请求

特点：

- 快
- 原子
- 适合高并发闸门

### 12.2 数据库库存

角色：

- 最终业务账本

特点：

- 可靠
- 可追溯
- 能和挂号单形成最终一致结果

### 12.3 两者关系

不是二选一，而是分工不同：

1. Redis 决定“谁有资格继续往下走”
2. 数据库决定“最终账本到底记成什么样”

---

## 13. 退号时为什么 Redis 和数据库都要回滚

取消挂号时，当前实现会同时做两件事：

1. 数据库库存 `available_count + 1`
2. Redis 库存 `schedule:stock:{scheduleId}` 也 `increment`

这是必须的。

如果只回数据库，不回 Redis：

- 系统入口仍然会认为没号

如果只回 Redis，不回数据库：

- 最终账本就不对

所以回滚库存时必须双写两层。

---

## 14. 这套方案到底优化了什么

很多人第一次看到本地消息表会问：

- “那成功请求不是还是要写数据库吗？”

答案是：对，成功请求还是要写数据库。

但它优化的是：

- **失败请求不再去打数据库**

举例：

- 300 并发
- 20 库存

没有 Redis 时：

- 300 个请求都可能打 DB

有 Redis 预扣后：

- 只有 20 个成功请求继续打 DB

这就是数量级上的差别。

所以当前架构的价值不是：

- 让数据库完全不写

而是：

- 把数据库写压力压缩到“真实成功请求”这一小部分

---

## 15. 当前方案还要注意的后续优化点

这次修的是“入口事务内 Redis 库存补偿”，但整条链路后面还有两个值得继续关注的点。

### 15.1 数据库扣减现在还是“先查再改”

在 `processRegistrationMessage()` 里，当前是：

1. 先查 `doctor_schedule`
2. 再 `available_count - 1`
3. 再更新

更稳的方式通常是条件更新：

```sql
update doctor_schedule
set available_count = available_count - 1
where id = ?
  and available_count > 0;
```

这样数据库层也能更强地防住并发和重复消费问题。

### 15.2 消费端长期失败时的 Redis 逆向补偿

如果消息始终消费失败，理论上会出现：

1. Redis 已经预扣
2. 本地消息在重试
3. 数据库迟迟没成功落账

这时是否需要死信队列、人工补偿、或者自动回补 Redis，要再设计清楚。

所以这次修掉的是：

- 请求入口事务内的一致性问题

不是：

- 整个异步链路从头到尾所有异常场景都完全闭环

---

## 16. 面试/汇报时可以怎么一句话概括

你可以这样说：

> 我们的挂号高并发方案采用 Redis 预扣库存作为入口闸门，先用限流和患者维度分布式锁挡住洪峰与重复点击；抢到号后不直接同步写挂号单，而是先落本地消息表，再由 Kafka 异步驱动数据库最终扣减和挂号单生成。这样既避免了高并发直接打数据库，又通过本地消息表和事务回滚补偿保证了库存与异步链路的一致性。

---

## 17. 最后再用一句最通俗的话总结

整条高并发挂号链路，其实就是：

1. 先用 Redis 快速抢号
2. 抢到的人把“我要挂号”这件事记进数据库消息表
3. 后面异步慢慢出票
4. 如果中间事务失败，就把 Redis 号补回去

你只要抓住这四句话，整个设计就不会乱。
